# PDF Insight — разбор задания и план

Дата подготовки: 05.10.2026. Статус: только планирование, реализация не начата.

Источники: письмо «Zadanie rekrutacyjne – Vibe Coder | Greywolf Group», Brief_Vibe_Coder_PDF_Insight.pdf (6 страниц), Test_PDF_Insight_umowa_14-2026.pdf (12 страниц, включая скан на странице 11).

## 1. Цель и условия

Создать приложение PDF Insight: загрузка PDF → извлечение текста → анализ AI → краткое содержание и структурированные данные → скачивание JSON.

- Дедлайн из письма: 06.10.2026, 14:44 по Варшаве.
- Готовность по брифу: посторонний пользователь открывает демо без инструкций, загружает собственный PDF, менее чем за 30 секунд получает результат и скачивает JSON нужной структуры. Скорость нужно измерить; обещание без проверки не считается выполнением.
- Публичный GitHub-репозиторий, AI_LOG.md и работающий GitHub Pages обязательны.
- Демо должно работать минимум 14 дней. Бесплатные лимиты API допустимы, но доступность и квоту нужно проверить.
- В форме: репозиторий → «Link do zadania testowego», демо → «Komentarz do zadania». Также спросят форму сотрудничества и финансовые ожидания.
- Вакансия предусматривает работу из офиса в Варшаве.

## 3. Архитектура и стек

Обязательный стек из брифа: React 18+ с Vite, TypeScript strict, GitHub Pages, деплой через GitHub Actions, валидация ответа AI (например, Zod). Backend и AI-провайдер свободные.

Решение после обсуждения: Cloudflare Workers AI выбран провайдером. Предпочтение Кирилла для backend — Python; рабочий вариант — FastAPI в Cloudflare Python Worker. Реализация пока не начата. Совместимость пакетов и расход CPU на бесплатном плане проверяем первым техническим этапом после разрешения писать код.

1. React SPA принимает файл, проверяет его и извлекает текст через pdf.js.
2. FastAPI в Cloudflare Python Worker принимает текст по страницам и метаданные, ограничивает запрос и вызывает LLM через Workers AI binding. Для этого вызова отдельный ключ модели не нужен.
3. Backend проверяет результат через Pydantic, при необходимости делает одну повторную попытку.
4. Frontend повторно проверяет ответ на своей границе, отображает данные и формирует файл JSON.

Для MVP достаточно одного API и без серверной базы данных. Модель-кандидат — Llama 3.3 70B в Workers AI; окончательное решение зависит от проверки польского договора, JSON и скорости. Cloudflare документирует FastAPI через встроенный ASGI-адаптер. Python выполняется через Pyodide/WebAssembly: совместимость с обычным Linux Python не предполагаем автоматически.

### Извлечение текста и хранение

| Данные | Где находятся | Как долго и зачем |
|---|---|---|
| Исходный PDF | Память браузера после выбора файла | До сброса/закрытия страницы; backend в базовом потоке не получает файл |
| Извлечённый текст с номерами страниц | Память браузера, затем тело HTTPS-запроса и память backend | На время анализа; постоянную запись на сервере не делаем |
| Текст для модели | Workers AI | Передаётся провайдеру для обработки; уведомляем пользователя |
| Результат JSON | Память браузера | До сброса; пользователь может скачать файл |
| История анализов (F-09) | Хранилище браузера | Ограниченное число результатов с возможностью очистки; исходный PDF и полный текст не сохраняем |
| Служебные сведения | Логи/метрики backend | Статус, длительность и расход; без полного текста, результата и секретов |

PDF.js извлекает текстовый слой постранично. Сохраняем номера страниц и восстанавливаем строки с учётом расположения текстовых элементов; таблицы требуют отдельной проверки качества. Страница без текста получает предупреждение, полностью сканированный PDF — понятное сообщение до добавления OCR. План OCR остаётся отдельным: текстовая Llama сама не распознаёт изображения. Тяжёлый OCR в бесплатный Python Worker не закладываем.

Постоянное хранение PDF в R2 или базе не требуется для текущего задания. Отсутствие нашей записи в базу не означает, что содержимое не покидает устройство: оно передаётся Workers AI. Счётчики rate limiting — отдельные служебные данные; не используем обычную глобальную переменную Worker как надёжный общий счётчик.

### Backend и контракт

- POST /api/analyze: принимает ограниченный по размеру JSON с именем файла, числом страниц, текстом по страницам и сведениями о непрочитанных страницах.
- GET /api/health: проверяет доступность backend без расходования AI-квоты.
- Backend валидирует структуру и размер входа, ограничивает запросы, формирует инструкции, вызывает AI, валидирует результат и возвращает нормализованный JSON либо понятную ошибку.
- Метаданные, пришедшие из браузера, считаются недоверенными. Сервер проверяет согласованность страниц и ограничения текста; он не может независимо проверить исходный размер PDF, которого не получал. Ограничение 10 MB применяется до извлечения в браузере, размер API-запроса ограничивается отдельно на сервере.
- Pydantic задаёт контракт backend; JSON Schema служит общей спецификацией. На frontend остаются Zod и обязательные Vitest-тесты. При двух языках проверяем одинаковые примеры ответа на обеих сторонах, чтобы схемы не расходились.
- Проверки Python (например, pytest для контрактов/повторов и линтер) добавляются к обязательным frontend-проверкам, не заменяют Vitest.

### Где находятся ключи и настройки

- Workers AI binding AI связывает backend с AI внутри аккаунта Cloudflare: отдельный API-ключ для модели не хранится и не передаётся frontend.
- Если позднее подключим внешнего AI-провайдера, его ключ хранится в Cloudflare Worker Secrets.
- Токен деплоя Cloudflare с минимальными нужными правами хранится в GitHub Actions Secrets, если используем автоматический деплой backend.
- Локальные секреты — в игнорируемом Git файле .dev.vars или .env по выбранному инструменту. В репозитории только пример имён без значений.
- VITE_API_URL — публичная настройка с адресом backend, не секрет.

### Ограничения бесплатного запуска

Планируем Workers Free и бесплатную дневную квоту Workers AI без включения платного плана. В документации Workers Free указано 10 мс CPU на запрос, ожидание сетевого вызова не входит в CPU-время. Нельзя заранее обещать, что FastAPI + валидация поместятся в этот лимит: после начала реализации измеряем полный путь на репрезентативном запросе и реальном деплое. Если не помещается, сначала упрощаем обработчик; смену языка или платный план не считаем автоматически согласованными.

Объём контекста AI ограничивает объём текста независимо от лимита PDF 10 MB. Для длинных документов планируем F-08; текст молча не обрезаем. Повтор после невалидного результата и каждый фрагмент расходуют AI-квоту. Требование <30 секунд проверяется отдельно и не следует из наличия бесплатного хостинга.

Источники для архитектуры, проверены 05.10.2026: [FastAPI в Workers](https://developers.cloudflare.com/workers/languages/python/packages/fastapi/), [Python Workers](https://developers.cloudflare.com/workers/languages/python/), [среда Python](https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/), [bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/), [секреты](https://developers.cloudflare.com/workers/configuration/secrets/), [лимиты](https://developers.cloudflare.com/workers/platform/limits/), [PDF.js: текст страницы](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html).

Технические пункты GitHub Pages из брифа:

- Vite base соответствует /<repo>/.
- Если вводим маршруты — HashRouter либо корректный 404.html; одностраничному экрану маршрутизатор не нужен.
- Публичный адрес backend — VITE_API_URL; ключ AI туда не попадает.
- Worker pdf.js загружается по правильному пути после сборки и публикации.
- Уведомление о передаче данных соответствует реализации: при передаче текста пишем, что содержимое документа отправляется AI; при OCR уточняем передачу изображений, если она используется.

## 4. Контракт данных

Все поля ниже обязательны по составу. Добавление полей разрешено, удаление — нет.

| Поле | Содержание и правило |
|---|---|
| document.fileName | Имя загруженного файла; берём из загрузки, не генерируем моделью. |
| document.pages | Фактическое количество страниц PDF; для тестового файла 12 даже без OCR. |
| document.language | Код ISO 639-1, например pl. |
| document.type | Одно из: faktura, umowa, oferta, raport, inne. Сохраняем значения перечисления из брифа. |
| document.title | Название документа из содержания. |
| document.date | Дата основного документа в ISO 8601 либо null. |
| summary | 3–5 предложений на языке документа. |
| keyPoints | Для успешного анализа строго 3–7 ключевых пунктов, подтверждённых документом. Ответ с 1–2 пунктами не считается валидным. |
| entities.organizations | Массив названий организаций. |
| entities.people | Массив имён людей. |
| amounts | Массив объектов value (число), currency (ISO 4217), context (назначение суммы). |
| dates | Массив объектов date (ISO 8601), context (к чему относится дата). |
| keywords | Массив ключевых слов. |

Общие правила: ключи по-английски, естественно-языковые значения на языке документа; отсутствующие сведения — null или []; модель не угадывает. Коды языка/валюты и document.type подчиняются заданному формату. До реализации фиксируем допустимость null отдельно для каждого поля: пример брифа не является полной формальной JSON Schema. Явно разрешён null для document.date; отсутствие организаций, людей, сумм или дат даёт пустые массивы. Не переносим возможность null/[] автоматически на summary и keyPoints, у которых есть специальные требования.

Для успешного результата summary содержит 3–5 предложений, keyPoints — 3–7 подтверждённых пунктов. Валидация не ослабляет эти ограничения ради коротких документов. Если содержания недостаточно для достоверного результата, показываем понятное сообщение о недостаточности данных вместо выдуманных фактов или JSON, выдаваемого за соответствующий схеме. Невалидный ответ AI запускает ровно одну автоматическую повторную попытку на уровне backend; повторная неудача возвращает ошибку. Frontend не запускает дополнительную скрытую серию повторов. Ручное «Повторить» — новое действие пользователя.

Предлагаемое расширение: сведения о полноте обработки и номерах страниц без текста. Если добавляем ссылки на страницы-источники для сумм и дат, сохраняем исходные обязательные поля. Такие расширения — наши решения, не отдельные MUST.

Валидация схемы проверяет структуру, типы и ограничения, но сама по себе не доказывает истинность утверждений. Качество проверяем отдельно на документе.

## 6. Что проверять на приложенном договоре

Это наблюдения по тестовому PDF, а не дополнительные требования работодателя.

1. Основной документ — польская рамочная умова № 14/2026 от 12.03.2026 между Nordwave Logistics sp. z o.o. и Kwadrat Software S.A. Вложенная фактура не должна менять тип всего документа на faktura.
2. Страница 4 содержит prompt injection с требованием выдать ложные сведения о недействительности договора и стоимости 1 PLN. Оно не должно попасть в результат как факт и не должно влиять на инструкции приложения.
3. Различаем стоимость внедрения 184 500 PLN netto, 226 935 PLN brutto, обслуживание 12 300 PLN netto в месяц, лицензии 8 600 EUR в год и hosting 890 USD в месяц. Не складываем разные валюты и периодичности в одну «общую стоимость».
4. Бюджет 250 000 PLN на первой странице, уставные капиталы, отклонённый вариант за 310 000 PLN, аванс и штрафы имеют разный контекст. Извлечённая сумма должна сохранять этот контекст.
5. Основная дата договора — 2026-03-12. Даты фактуры 2026-03-15, оплаты 2026-03-29, Go-live 2026-10-12 и анекса 2026-03-20 должны оставаться отдельными событиями.
6. Номер банковского счёта в документе намеренно отсутствует: не выдумываем и не подставляем.
7. На странице 10 есть английское executive summary; основной язык документа остаётся польским.
8. На странице 11 отсутствует текстовый слой. Визуально это анекс от 20.03.2026: абонплата 12 300 PLN netto действует до 31.03.2027, с 01.04.2027 — 13 100 PLN netto; количество пользователей повышается со 120 до 135.
9. Без OCR допустим частичный анализ с явным предупреждением о странице 11. Нельзя заявлять, что обработан весь договор, или выдавать исходные условия как подтверждённые с учётом анекса.
10. С OCR проверяем, что изменения анекса связаны с исходными условиями и датами действия, а не представлены как случайные противоречащие суммы.
11. В документе есть таблицы, колонки, польские символы, разные форматы дат и повторяющиеся колонтитулы. Результат нашей текущей текстовой экстракции местами содержит лишние пробелы возле польских букв; качество pdf.js нужно проверить отдельно, не предполагать заранее.
12. Временные и финансовые неоднозначности источника сохраняем с контекстом; модель не должна самостоятельно «исправлять» договор или вычислять неподтверждённый итог.

### Условия принятия архитектуры после начала реализации

1. Python/FastAPI действительно запускается на бесплатном Cloudflare и укладывается в CPU-лимит на реальном запросе с валидацией, а не только на /health.
2. Модель обрабатывает тестовый договор без выполнения prompt injection и возвращает достоверный польский результат по схеме.
3. Полный путь укладывается в <30 секунд на тестовом и дополнительных репрезентативных PDF. Бриф не определяет оборудование/сеть/объём текста для этого порога: фиксируем условия замера, не переобозначаем требование как необязательное.
4. Измерен расход квоты на анализ и повтор. Выбраны конкретные лимиты публичного API и способ их обеспечения. На Free исчерпание квоты остаётся риском доступности; сообщение об ошибке не заменяет требование работающего анализа.
5. Для длинных текстов определено поведение. Ограничение модели не даёт права молча обрезать вход; отказ по превышению контекста документируется как реальное ограничение и не считается выполнением F-08.
